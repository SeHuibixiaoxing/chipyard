# MudnacSim × HybridMapper 协同机制文档（v2）

- 版本：v2
- 日期：2026-03-07
- 范围：`HybridMapper（编译侧） + MudnacSim（执行侧） + 脚本链路`
- 相比 v1 的增补：
  - 增加“实验脚本参数矩阵与推荐运行方式”
  - 增加“严格版 YAML schema”
  - 增加“单 subgraph 文本时序图”
  - 风险改写为“问题-影响-建议”

## 1. 总体协同架构

### 1.1 角色边界

- HybridMapper：离线生成模型结构、逐层 mapping、图划分候选、pipeline 候选、schedule point 候选与 profiling 聚合结果。
- MudnacSim：读取上述产物，做资源分配、pipeline 执行、QoS 调度与时延统计。
- 脚本层：负责参数枚举、批量执行、日志解析、`profiline.yaml` 回填和 `schedule_point_profiling_<method>.yaml` 聚合。

### 1.2 主数据流

1. `create-pipeline-model-mapping.py` 生成 `layers.yaml`、`layers.dump`、`mapping/<layer>.yaml/.dump`。
2. `create-pipeline-model-partition.py` 生成 `model_partition.yaml/.dump`。
3. `create-pipeline-sasearch-single-model.py` 生成全模型 pipeline mapping：`entire_model/*.yaml`。
4. `create-pipeline-schedule-point.py` 与 `create-pipeline-schedule-graphpartition.py` 生成 schedule point 和分段 partition。
5. `create-pipeline-schedule-sasearch.py` 为每个分段生成 `schedule_point/pipeline_mapping/<partition>/<seg>/*.yaml`。
6. `expr_single_pipeline_profiling.py` 批量运行单 segment 仿真。
7. `create_single_pipeline_profiling_read_log.py` 把仿真日志回填为各 segment 的 `profiline.yaml`。
8. `create-schedule-point-profiling-file.py` 聚合为 `schedule_point_profiling_<method>.yaml`。
9. `expr_qos_pipeline.cpp` / `ThreadQoSPipeline` 在运行时用 `target` 检索对应 `mapping_path`，逐 subgraph 执行。

### 1.3 路径协同关键点

- `tmp/MudnacSim/models` 是指向 `../HybridMapper/output/` 的符号链接。
- 因此 MudnacSim 代码中使用的 `models/pipeline/...`，本质上直接消费 `tmp/HybridMapper/output/pipeline/...`。
- 这也是编译侧与执行侧最核心的“文件系统契约”。

## 3. 模型划分机制

### 3.1 图元数据准备

- `Model._generate_graph_info` 预先生成：
  - segment 内 tensor 入度/出度
  - segment 内 tensor 最小/最大尺寸
  - 每层输入/输出/权重 tensor 集合
- 代码：`tmp/HybridMapper/HybridMapper/Model.py:508`

### 3.2 段内 acc 分配

- `GraphPartitioner.search_segment` 对固定 layer 区间做段内 DP。
- 每层代价由 compute、dram、noc 三部分共同约束。
- 输出内容包括：
  - 段内每层 acc 分配
  - 每层估计执行时间
  - 是否 compute bound
  - 实际使用的 acc 数
- 代码：`tmp/HybridMapper/HybridMapper/GraphPartition.py:175`

### 3.3 全局 segment 划分

- `GraphPartitioner.partition` 从后向前枚举边界，把“当前 segment 成本 + 剩余部分成本”做全局最优组合。
- 输出的 `partition_plan` 和 `acc_plan` 成为后续 SA 的起点。
- 代码：`tmp/HybridMapper/HybridMapper/GraphPartition.py:278`

## 4. 网络层划分机制

### 4.1 SA 状态空间

- `GraphPartitionSimulatedAnnealing` 维护三类核心状态：
  - `partition_plan`
  - `acc_plan`
  - `tensor_type` / `tensor_meta_type`

### 4.2 tensor 类型到运行时行为的映射

- 编译侧 `TensorType` 会被转换成运行时 `TensorTypeRuntime`：
  - `DRAM`
  - `DRAM_DEPEN`
  - `ISOLATE_SPM`
  - `SHARED_SPM`
  - `ALL_RINGBUFFER`
- 代码：`tmp/HybridMapper/HybridMapper/StageRecord.py:198`

### 4.3 ring buffer 触发条件

- `SegmentSolution._generate_ring_buffer` 按 tensor 的 meta type、所在 stage 深度差和消费关系决定是否开启 ring buffer。
- 产出：
  - `ring_buffer_count`
  - `ring_buffer_size_per`
  - `ring_buffer_use_count`
  - `ring_buffer_use_spm`
- 代码：`tmp/HybridMapper/HybridMapper/SASearch.py:305`

### 4.4 SPM 需求汇总

- `SegmentSolution._generate_spm_need` 汇总四部分需求：
  - `tensor_spm_util_in_stage`
  - `tensor_spm_util_shared`
  - `tensor_spm_util_in_ringbuffer`
  - `tensor_spm_util_weight`
- 代码：`tmp/HybridMapper/HybridMapper/SASearch.py:383`

### 4.5 代价评估

- `SegmentSolution.evaluate` 使用 pipeline fill/drain 公式估算 exec cost。
- 当 `enable_decoupling=True` 时按整段总 SPM 判断；否则按 stage 独立容量判断。
- 超限直接加 penalty，不在该层做运行时修复。
- 代码：`tmp/HybridMapper/HybridMapper/SASearch.py:398`

## 6. pipeline buffer 机制

### 6.1 数据结构

- `PipelineBuffer` 维护：
  - `pSpmPages[2]`
  - `bufferHasFullData[2]`
  - `cmdRunning[2]`
  - `fetchFlushSendCmdCounts[2]`
  - `dramBaseAddr[2]`
  - `subBatchOffset`
- `RingBuffer` 维护：
  - `size_`
  - `head_`
  - `tail_`
  - `use_count_`
  - `out_degree_`
- 代码：`tmp/MudnacSim/src/runtime/pipeline_buffer.h:7`

### 6.2 五类 TensorStayType

- `DRAM`：入口从 DRAM fetch，出口向 DRAM flush。
- `DRAM_DEPEN`：同样走 DRAM，但需要满足上下游 subBatch offset 依赖。
- `ISOLATE_SPM`：stage 间通过 send/fetch 传输，前后 stage 不共享同一组页。
- `SHARED_SPM`：前后 stage 共享同一组 SPM 页。
- `ALL_RINGBUFFER`：数据完全驻留在 ring buffer 逻辑中，不再给普通 pipebuffer 预留独立存储语义。
- 类型定义：`tmp/MudnacSim/src/runtime/mapping.h:65`

### 6.3 ring buffer 语义

- `fill(subBatchOffset)`：表示对应 sub-batch 生产完成，`tail_++`，并初始化使用计数。
- `use(subBatchOffset)`：表示某个消费者消费完成，`use_count--`；若该 offset 的使用计数清零且它正位于 `head_`，则推进 `head_`。
- 代码：
  - `tmp/MudnacSim/src/runtime/pipeline_buffer.cpp:65`
  - `tmp/MudnacSim/src/runtime/pipeline_buffer.cpp:52`

## 7. SPAD(SPM) 管理机制

### 7.1 资源入口

- `PipelineRuntime::GenerateAction` 先分配 acc，再分配 SPM。
- `ReleaseAction` 统一回收 weight/in-stage/ring-buffer 页。
- 代码：`tmp/MudnacSim/src/runtime/runtime.cpp:852`

### 7.2 `ALL_BANK_PAGE_INTER`

- 一次性从全部 bank 交错取页。
- 分配顺序为：
  - weight
  - in-stage tensor
  - shared tensor
  - ring buffer
- 代码：`tmp/MudnacSim/src/runtime/runtime.cpp:962`

### 7.3 `MIN_DIS`

- 先从“相关 stage 所在 acc 集”对应 bank 优先分配。
- 如不足，则按照和 preferred bank 的曼哈顿距离从近到远扩展。
- 目标是让张量尽量落在物理位置接近的 bank 上。
- 代码：`tmp/MudnacSim/src/runtime/runtime.cpp:1111`

### 7.4 页分配器本体

- `SPMManager` 提供：
  - `allocateFromBank`
  - `allocateFixedBankInterlace`
  - `allocateAllBankInterlace`
  - `freePages`
- 代码：`tmp/MudnacSim/src/runtime/spm_manager.cpp:1`

### 8.2 线程状态机

- `ThreadQoSPipeline::tick` 的关键状态：
  - 取任务
  - 等待 dispatch 时间
  - 做资源目标调整
  - 选择当前 subgraph 的 mapping
  - 创建 `ThreadRunPipeline`

- 再调用 `PipelineMappingParser::pipelineCandidateToPipelineMapping` 装载实际执行配置。

## 10. 实验脚本参数矩阵与推荐运行方式

### 10.1 HybridMapper 脚本矩阵

| 脚本 | 主要参数/常量 | 作用 | 推荐用途 |
|---|---|---|---|
| `create-pipeline-models.py` | `--models`、`--stages`、`--max-iter`、`--num-proc` | 总编排入口 | 日常驱动全链路 |
| `create-pipeline-sasearch-single-model.py` | `ACC_CANDIDATES=[8,16,24,32]`、`SPM_PER_ACC_CANDIDATES_KB=[256,512,1024,2048]`、`DEFAULT_BATCH_CANDIDATES=[16,32]`、`METHOD=[ours2,gemini2,tangram2]` | 生成全模型 mapping | 做单模型 pipeline 候选 |
| `create-pipeline-schedule-point.py` | `ACC_CANDIDATES=[8]`、`SPM_PER_ACC_CANDIDATES_KB=[1024*1024]`、`SCHEDULE_POINT_NUM=[3,4,5,6]` | 生成 schedule point | 固定分段数方案探索 |
| `create-pipeline-schedule-sasearch.py` | 读取 schedule point dump + partition dump | 生成每个分段的 mapping | QoS 分段运行前的离线准备 |
| `create-schedule-point-profiling-file.py` | `--models` | 聚合 `profiline.yaml` | 供执行侧 QoS 读取 |

### 10.2 MudnacSim 脚本矩阵

| 脚本 | 主要参数/常量 | 作用 | 推荐用途 |
|---|---|---|---|
| `expr_single_pipeline_profiling.py` | `accList=[8,16,24,32]`、`batch_size=[16]`、`PARTITION_NUM=[3]`、`METHOD=[ours,gemini,tangram]`、`spm_per_bank_list=[1024]` | 跑单 segment profiling | 对 schedule point 分段做实测 |
| `create_single_pipeline_profiling_read_log.py` | `--log-dir`、`--project-root` | 解析 `Total Latency` 并回填 `profiline.yaml` | profiling 后处理 |

### 10.3 推荐运行方式

- 日常增量更新：优先按 stage 跑，不建议每次全链路重做。
- 当模型结构或逐层 mapping 变化时：跑 `MC,LM,GP,EMSA`。
- 当只改 schedule point / 调度策略时：跑 `SP,SPGP,SPSA,SPPF`。
- 当只需要更新 QoS 实测 cost 时：只重跑 `expr_single_pipeline_profiling.py` 和 `create_single_pipeline_profiling_read_log.py`，无需重做 SA。
- 当只验证单模型 mapping 是否可执行时：直接用 `entire_model/*.yaml` 配合 `expr_single_pipeline`，不要先走 schedule point 链路。

## 12. 单 subgraph 文本时序图

下面描述的是 QoS 模式下“一个 task 的一个 subgraph”从选图到执行完成的时序。

1. `ThreadQoSPipeline` 进入 `STATE_CREATE_PIPELINE_THREAD`。
2. 它根据当前线程资源目标，调用 `GenerateTargetFromIdx(acc_idx, spm_idx, model_idx)`。
3. `PipelineProfilingResult.get(target)` 返回该 target 的 `cost[]` 和 `mapping_paths[]`。
4. `ThreadQoSPipeline` 取 `mapping_paths[cur_subgraph_idx]` 作为当前 subgraph 的 mapping。
5. `PipelineMappingParser::pipelineCandidateToPipelineMapping(model, mapping_path)` 解析 YAML，得到 `PipelineMapping`。
6. `ThreadRunPipeline` 被创建，但此时内部只会顺序执行该 mapping 内的 segmentCandidates。
7. 当前 segment 启动时，`ThreadRunSegment::tick` 调用 `GenerateAction`。
8. `GenerateAction` 内部依次做：
   - `AllocAcc`
   - `AllocSpm`
9. `Pipeline::tick` 进入配置期：
   - 建 pipebuffer
   - 建 ringbuffer
   - 建 stages
10. `Stage::tick` 先对固定张量发 `fetch`，再等待入口 pipebuffer ready。
11. 当入口 buffer 满、出口 buffer 空时，stage 启动 layer 执行。
12. `Pipeline` 在每个时钟周期同时推进：
   - 入口 fetch
   - 出口 flush
   - stage 间 send/share
   - ring buffer head/tail/use_count 更新
13. 当该 subgraph 的最后一个 segment 执行完成后，`ReleaseAction` 回收 acc 与 SPM 页。
14. `ThreadQoSPipeline` 记录该 subgraph 的开始/结束时间、估计时间、slack，并决定是否切到下一个 subgraph 或结束 task。

## 13. 风险与实现现状（问题-影响-建议）

### 13.1 CMake 源文件引用漂移

- 问题：`tmp/MudnacSim/CMakeLists.txt:1` 引用了当前仓库中不存在的 `qos_scheduler_new.cpp`、`thread_qos_pipeline_new.cpp` 等文件。
- 影响：完整构建配置与源码树状态不一致，后续若放开对应 target，构建会直接失败。
- 建议：把 CMake 中缺失文件改成条件编译或删掉悬空引用，并明确当前正式入口 target。

### 13.2 profiling target 等价判定不完整

- 问题：`PipelineProfilingResult::Target::operator==` 未比较 `model_idx`，但 `Hash::operator()` 包含了 `model_idx`：
  - `tmp/MudnacSim/src/runtime/runtime.cpp:2036`
  - `tmp/MudnacSim/src/runtime/runtime.cpp:2060`
- 影响：`unordered_map` 的 key 等价关系和哈希维度不完全一致，存在隐含检索风险，尤其在多模型 QoS 场景下更敏感。
- 建议：让 `operator==` 与 `Hash` 使用完全相同字段集合。

### 13.3 执行侧 `dram_bw` 组装硬编码

- 问题：`GenerateTarget` 里把 `target.dram_bw` 固定为 `19`：`tmp/MudnacSim/src/runtime/runtime.cpp:943`
- 影响：当 profiling 文件里存在其他 `dram_bw` 维度时，运行时 target 可能找不到匹配项。
- 建议：直接从 runtime 配置或 profiling 可用集合中取当前值，避免硬编码。

### 13.4 schedule point 目标构造语义偏移

- 问题：`create-pipeline-schedule-point.py` 中 `Target(numArrays=512, ...)`，而真正参与分段映射搜索的 acc 候选又是 8/16/24/32 这一类值：`tmp/HybridMapper/scripts/create-pipeline-schedule-point.py:1`
- 影响：schedule point 的“切分依据”与后续真实执行 target 的语义不完全同构，容易让读代码的人误判其含义。
- 建议：在脚本中显式注释“512 仅用于初始化单层段 cost 的上限视角”，或者改成更自解释的构造方式。

### 13.5 当前主链路状态

- 问题：代码中存在上述局部风险，但主干文件契约仍然统一。
- 影响：对于现有仓库产物，`HybridMapper 输出 -> MudnacSim parser -> pipeline 执行 -> profiling 聚合 -> QoS 调度` 的主链条是连通的。
- 建议：后续维护时优先守住“路径契约、字段契约、target 维度契约”三条主线。
