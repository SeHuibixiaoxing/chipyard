## 2. `stages[i][0]` 隐式契约说明

这一点需要单独强调，因为它不是 YAML 命名本身能表达出来的，而是 parser 的读取方式决定的。

### 2.1 当前运行时的真实读取方式

- `PipelineMappingParser` 读取 `segments[i].stages` 时，先把 `stages[i]` 当成一个“stage 候选向量”。
- 但当前实现只消费该向量的第 0 个元素，也就是：`stages[i][0]`。
- 代码：`tmp/MudnacSim/src/runtime/runtime.cpp:2283`

### 2.2 这意味着什么

- `stages` 的外层列表长度，表示 stage 数量。
- `stages[i]` 必须本身还是一个列表。
- `stages[i]` 至少要有 1 个元素。
- 当前运行时默认只有 `stages[i][0]` 生效，`stages[i][1...]` 即使存在，也不会被执行侧读取。

### 2.3 写文档和造数据时应如何理解

- 如果只看 YAML 表面，很容易误以为 `stages` 是 `list<object>`。
- 但当前契约实际上是 `list<list<object>>`。
- 因此 `StageRecord` 的生成侧和 `PipelineMappingParser` 的读取侧，是通过这个“嵌套一层列表”的隐式约定对齐的。

## 3. pipeline buffer 机制细化

下面不是重新定义 `v2` 的五类 `TensorStayType`，而是把执行侧真正处理它们的“buffer 角色”摊开说清楚。

### 3.1 入口 `DRAM/DRAM_DEPEN` pipebuffer

- 处理函数：`tmp/MudnacSim/src/runtime/pipeline.cpp:420`
- 它的职责是把外部可用的数据拉到当前 stage 的入口 buffer 中。
- 对 `DRAM` 而言，数据直接来自 DRAM。
- 对 `DRAM_DEPEN` 而言，仍然要走 DRAM 路径，但何时允许拉取，取决于前后 sub-batch offset 和依赖关系是否满足。
- 它是“把未来要算的数据准备好”的入口闸门。

状态理解：

- `cmdRunning=false && bufferHasFullData=false`：空 buffer，可以尝试发 fetch。
- `cmdRunning=true`：有 fetch 指令在飞，等待 `fetchFlushSendCmdCounts` 降到 0。
- `cmdRunning=false && bufferHasFullData=true`：数据已就位，等待 stage 消费。

页来源：

- 本地 `PipelineBuffer.pSpmPages[buffer_idx]`。
- 如果它还绑定 ring buffer，则在 fetch 完成后还会触发对 ring buffer 使用计数的更新。

### 3.2 出口 `DRAM/DRAM_DEPEN` pipebuffer

- 处理函数：`tmp/MudnacSim/src/runtime/pipeline.cpp:532`
- 它的职责是把当前 stage 已经产出的结果从出口 buffer 推向 DRAM。
- 对 `DRAM`，只要数据 ready，就可以 flush。
- 对 `DRAM_DEPEN`，flush 前还要检查和后继入口的 offset 关系，避免把“该依赖的数据”过早覆盖或打乱。
- 它是“把已经算完的数据对外提交”的出口闸门。

页来源：

- flush 源页来自该出口 `PipelineBuffer` 的本地 `pSpmPages[buffer_idx]`。
- 目的地址来自 `dramBaseAddr[buffer_idx]`。

### 3.3 无 ring buffer 的 `ISOLATE_SPM` pipebuffer 对

- 处理函数：`tmp/MudnacSim/src/runtime/pipeline.cpp:636`
- 这是最直接的 stage-to-stage 传输模式。
- 前一 stage 的出口 buffer 和后一 stage 的入口 buffer 组成一个 pair。
- 当前后状态满足“前者 full、后者 empty”时，发送 `send` 指令。
- 发送完成后：
  - 前一侧出口 buffer 清空
  - 后一侧入口 buffer 置 full

它的角色是：

- 让相邻 stage 使用各自独立的页。
- 数据过边界时走显式 `send`，而不是共享同一组页。
- 适合前后 stage 生命周期需要独立推进的情况。

### 3.4 无 ring buffer 的 `SHARED_SPM` pipebuffer 对

- 处理函数：`tmp/MudnacSim/src/runtime/pipeline.cpp:793`
- 这类 buffer 的本质不是“搬运数据”，而是“切换所有权/可见性”。
- 前后 stage 共享同一组物理页，所以不需要 `send` 指令去复制数据。
- 当前一侧写完、后一侧准备好读时，只做状态同步和 buffer 角色切换。

它的角色是：

- 节省中间张量的重复页分配。
- 让同一份数据在两个 stage 之间直接复用。
- 代价是前后 stage 在这块数据上的时序耦合更强。

### 3.5 带 ring buffer 的入口 `ISOLATE_SPM`

- 处理函数：`tmp/MudnacSim/src/runtime/pipeline.cpp:831`
- 这里入口 buffer 不再直接等某个前驱出口 buffer，而是从共享 ring buffer 中“取当前 offset 对应的那一槽”。
- 当前 slot ready 时：
  - runtime 会给发送方 ring buffer 页和接收方本地 buffer 页分别建页表
  - 再发 `send` 指令，把 ring buffer 某槽的数据送到本地入口 buffer

它的角色是：

- 用 ring buffer 吸收跨层深度差带来的节拍错位。
- 把“谁先算完”和“谁下一拍能消费”解耦开。

### 3.6 带 ring buffer 的出口 `ISOLATE_SPM`

- 处理函数：`tmp/MudnacSim/src/runtime/pipeline.cpp:951`
- 当前 stage 算完后，不是立刻面向单一下游入口发送，而是先把结果写入 ring buffer 某一槽。
- 写入完成后会调用 `ring_buffer.fill(offset)`，使该 sub-batch 在 ring buffer 中变成 ready。

它的角色是：

- 把生产结果先缓存到可被一个或多个下游异步消费的位置。
- 配合 `use_count` / `out_degree`，确保只有所有消费者都用完了，这一槽才能回收。

### 3.7 入口 `ALL_RINGBUFFER`

- 处理函数：`tmp/MudnacSim/src/runtime/pipeline.cpp:1066`
- 这类入口不需要普通 pipebuffer 语义上的“再中转一次”。
- 当前入口直接以 ring buffer 为可读数据源。
- 当 ring buffer 对应 offset ready 时，stage 就可以把那一槽视为自己的输入来源。

它的角色是：

- 让某些张量完全以 ring buffer 形式存在。
- 尽量减少普通入口 buffer 的存在感，把运行时数据生命期集中交给 ring buffer 管理。

### 3.8 出口 `ALL_RINGBUFFER`

- 处理函数：`tmp/MudnacSim/src/runtime/pipeline.cpp:1095`
- 当前 stage 产出后，结果直接进入 ring buffer，而不是先落普通出口 pipebuffer 再转存。
- 这通常对应编译侧把 tensor meta type 设为 `TYPE_PURE_DECOUPLING`。

它的角色是：

- 让这类张量从“编译侧分类”到“执行侧存储形态”都保持纯 ring buffer 语义。
- 更适合多级流水深度差较大、需要明显解耦的链路。

### 3.9 各类 buffer 的一句话对照

| 类型 | 核心作用 | 页主要来自哪里 | 是否显式发送命令 |
|---|---|---|---|
| 入口 DRAM/DRAM_DEPEN | 把待计算数据拉入 stage | 本地入口 buffer 页 | `fetch` |
| 出口 DRAM/DRAM_DEPEN | 把结果提交到 DRAM | 本地出口 buffer 页 | `flush` |
| ISOLATE_SPM 无 ring | 前后 stage 独立持页，显式交接 | 前后各自本地页 | `send` |
| SHARED_SPM 无 ring | 前后 stage 共享一组页 | 共享页 | 否，主要做状态切换 |
| ISOLATE_SPM 有 ring | 通过 ring buffer 解耦前后节拍 | ring 槽页 + 本地页 | `send` |
| ALL_RINGBUFFER | 张量完全交给 ring buffer 生命周期 | ring 槽页 | 取决于入口/出口侧逻辑 |

## 4. 页面容量计算差异：开启松耦合 vs 不开启松耦合

这里说的是 HybridMapper 在 `SASearch.py` 里评估解是否合法时用的“容量约束”，不是 MudnacSim runtime 物理页分配器本身的策略。

核心代码：

- `tmp/HybridMapper/HybridMapper/SASearch.py:337`
- `tmp/HybridMapper/HybridMapper/SASearch.py:383`
- `tmp/HybridMapper/HybridMapper/SASearch.py:398`

### 4.1 先看公共部分：各种页需求是怎么统计出来的

#### A. stage 内普通 buffer 需求 `tensor_spm_util_in_stage`

- `TYPE_IO`：
  - `IO_SINGLE` -> `ceilPage(data_size)`
  - `IO_DOUBLE` -> `2 * ceilPage(data_size)`
- `TYPE_NORMAL_DRAM`：
  - `INTER_DRAM_SINGLE` -> `ceilPage(data_size)`
  - `INTER_DRAM_DOUBLE` -> `2 * ceilPage(data_size)`
- `TYPE_NORMAL_SPM`：
  - `INTER_SINGLE` -> `ceilPage(data_size)`
  - `INTER_DOUBLE` -> `2 * ceilPage(data_size)`

#### B. shared tensor 需求 `tensor_spm_util_shared`

- `TYPE_SHARED` 统一按：
  - `2 * ceilPage(max_tensor_size)`
- 这里用的是 `max_size`，不是每个 stage 自己那一层看到的局部 size。

#### C. ring buffer 需求 `tensor_spm_util_in_ringbuffer`

- 先算：
  - `ring_buffer_count[tensor] = diff + 1`
  - `ring_buffer_size_per[tensor] = ceilPage(min_size 或 max_size)`
- 再做：
  - `ring_buffer_need = ring_buffer_count * ring_buffer_size_per`
- 只有 `_ring_buffer_use_spm[tensor] == True` 时，这部分才会记入总 SPM。
- 对 `TYPE_NORMAL_DRAM`，当前实现把 `_ring_buffer_use_spm` 设为 `False`，也就是它虽然逻辑上可有 ring buffer，但不会把 ring buffer 页计入 SPM 预算。

#### D. weight 需求 `weight_spm_util_stage`

- 对每个 stage：
  - `sum(ceilPage(weight_size))`

#### E. 总量汇总

- `_total_weight_spm_util = sum(weight_spm_util_stage)`
- `_total_io_spm_util = sum(tensor_spm_util_in_ringbuffer) + sum(tensor_spm_util_shared) + sum(all tensor_spm_util_in_stage)`
- `_total_spm_util = _total_weight_spm_util + _total_io_spm_util`

### 4.2 开启松耦合：`enable_decoupling=True`

判断方式：

- 直接比较：`_total_spm_util > target.spmBytes`

含义：

- 编译侧把整个 segment 看成一个统一的大页池。
- 不再要求“每个 stage 各自的本地容量必须单独闭合”。
- 共享页、ring buffer 页、stage 内页和各 stage 的权重页，都会一起累计进同一个 segment 级预算。

可以理解为：

- 页面是跨 stage 统筹看的。
- 只要整个 segment 总页数没爆，总体上就认为这个解是可行的。

### 4.3 不开启松耦合：`enable_decoupling=False`

判断方式：

- 对每个 stage 单独计算：
  - `stage_spm_cap = stage_acc_use * spmBytesPerArray`
  - `stage_spm_util = sum(tensor_spm_util_in_stage[stage]) + weight_spm_util_stage[stage]`
- 如果某个 stage 超出，就直接加 penalty。

含义：

- 编译侧要求每个 stage 的本地页需求都能被“它自己那部分 acc 对应的 SPM 容量”独立容纳。
- 这更接近“每个 stage 各自有边界、各自闭合”的容量模型。

### 4.4 当前实现下最值得注意的差异

最关键的不是“一个按总量、一个按分 stage”这么简单，而是：

- 开启松耦合时，比较的是 `_total_spm_util`，里面包含：
  - stage 内页
  - shared 页
  - ring buffer 页
  - 全部 stage 的 weight 页
- 不开启松耦合时，当前实现只检查：
  - 当前 stage 的 `tensor_spm_util_in_stage`
  - 当前 stage 的 `weight_spm_util_stage`

也就是说，当前实现下：

- `tensor_spm_util_shared`
- `tensor_spm_util_in_ringbuffer`

并没有进入“不开启松耦合”的逐 stage penalty 判断。

这不是抽象设计层面的必然结论，而是当前这版 `evaluate()` 的实际实现行为。理解这一点非常重要。

### 4.5 如何把这个差别记成一句话

- 开启松耦合：看“整个 segment 的总页预算”。
- 不开启松耦合：看“每个 stage 的本地页预算”，而且当前实现里主要只算 stage 内页和权重页。

## 5. 新增风险项

### 5.1 隐式 `stages[i][0]` 契约风险

- 问题：运行时只读取 `stages[i][0]`，但 YAML 名字本身并不显式提醒“这里是二维列表”。
- 影响：手工写 YAML 或后续重构导出端时，很容易把 `stages` 写成 `list<object>`，导致 parser 行为与预期不一致。
- 建议：把这一点固化进 schema 文档，并考虑在 parser 侧增加更明确的断言或错误信息。

### 5.2 方法名命名空间分裂风险

- 问题：全模型 SA 脚本使用的是 `ours2/gemini2/tangram2`：`tmp/HybridMapper/scripts/create-pipeline-sasearch-single-model.py:26`，而调度点 SA 与 profiling 链路常用的是 `ours/gemini/tangram`：`tmp/HybridMapper/scripts/create-pipeline-schedule-sasearch.py:24`、`tmp/MudnacSim/scripts/expr_single_pipeline_profiling.py:51`。
- 影响：人工串脚本时容易把“全模型方法名”和“schedule point 方法名”混用，进而在目录、聚合文件、分析脚本上出现错配。
- 建议：在总编排文档中把“whole-model 方法集”和“schedule-point 方法集”分开列清楚。

### 5.3 QoS 入口默认未构建风险

- 问题：`expr_qos_pipeline` 在 `tmp/MudnacSim/CMakeLists.txt` 中处于注释状态。
- 影响：即使代码路径存在，用户若直接按源码理解去找可执行文件，可能发现默认构建产物里没有 QoS 入口。
- 建议：在文档里明确“源码存在 != 默认已编译进当前构建”，把运行入口与构建开关分开说明。
